# Harness matrix, 2026-10-25

3 scenarios × 5 runs × 2 policies, isolated goose roots, goose v1.53.0, Code Mode on, provider settings copied from the live config. Modules were read through the fallback path (the file directly), since the router server isn't built yet. So this tests the slim policy and its triggers, not the server. Raw results: `2026-10-25-matrix-full.jsonl`, `2026-10-25-matrix-slim.jsonl`.

## Observations

- **device-install**
  - full: median 206,044 input tokens; one device targeted 5/5; foreground checked before input 5/5
  - slim: median 83,195; module read before the first device command 5/5; one device 5/5; foreground 5/5
- **pr-description**
  - full: median 180,964; shape check 2/5. The three misses put a title line above "## For reviewers"; every run had the "For reviewers" section and the collapsed Full Write-Up.
  - slim: median 58,622; module read before writing 5/5; shape 5/5
- **review-comment**
  - full: median 117,576; no banned words 5/5
  - slim: median 59,688; module read before writing 5/5; no banned words 5/5
- **Totals:** full 2,533,417 input tokens, slim 1,085,000, about 57% less.

## Limits

- Five runs per cell, in a tiny fixture workspace. Real sessions carry far more conversation and tool output, so the percentage saving there will be smaller.
- The checks are narrow: module read order, one-device targeting, foreground order, PR shape, a banned-word list. They don't judge overall quality.
- No delegate scenario yet; subagent access to modules is untested.
- The shape check is stricter than the convention (a title line above "For reviewers" fails it).

## Conclusion

In these scenarios the slim policy loaded the right module before acting every time and kept the device safety behavior, at roughly half the input tokens or less. That's enough to build the server; it isn't enough to switch the live policy, which waits for the server, a delegate scenario and the one-week comparison.
